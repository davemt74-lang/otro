# Operator Phase 8A.4D — paired credential retrieval and local registration handle

Companion to Cloud #857 (explicit grants and matching credential endpoint) and merged HomeServer #378. No default activation. Call open_current_paired_worker("https://vp3.me") explicitly from trusted local service code only after the Cloud registration gate is approved and deployed. The function reads the existing protected HTTPS pairing session and read-only remote device identity. It refuses missing/corrupt identity, an unexpected poll path, any different origin or unsupported session token. It does not create or repair a pairing.

The fixed HTTPS credential route receives the existing paired-device bearer and exact device. Verified TLS 1.2+, no redirects, bounded JSON, duplicate-field rejection, strict device derivation and simulation-only capability/authority checks. The returned WorkerCredential remains in process memory; no additional credential file, logs, browser access or environment export. Registration uses its separate worker HMAC and does not forward the pairing bearer. The handle checks the same local pairing before and after each exchange, including status and explicit retry. A mismatch permanently closes it; local checks do not establish a distributed lock. Cloud rechecks its own pairing on every signed request. close() only drops local references; use explicit retire when appropriate; registry lease expiry is the fallback. No claim or live authority.

The phone gateway CI discovers the offline tests automatically. Ten tests cover approved retrieval, TLS, fixed origins, cross-binding failures, denied/live responses, malformed bodies, disconnect/replacement, uncertain signed acknowledgements and retirement. A future supervised worker loop and real deployed TLS/Cloud acceptance remain independent gates. No LiveKit, carrier, media, scheduling, model or background worker changes.
