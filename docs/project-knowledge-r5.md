# R5 — Project Knowledge in Agent Chat

The Cloud, native and Chrome Chat canvases expose a **Project Knowledge** panel. Search saved browser annotations by text, exact tag, existing Research project, personal Knowledge folder and inclusive UTC capture date range. Results paginate in groups of 25. Annotations remain account-owned; removing project membership does not transfer or expose someone else's Knowledge.

**Use in Chat** rechecks access and inserts a bounded source quote, note, tags, capture date and source URL into the composer. The user sends the turn. Browsing, selecting and saving organization never starts a model run.

**Edit organization** edits the note, tags, Research project and Knowledge folder. The canvas shows old/new values before **Save reviewed changes**. The existing capture quote and pinned browser source version remain unchanged. One InnoDB transaction updates the original capture's note, delivery metadata, project membership and existing personal Knowledge item, rebuilding canonical chunks. Original Chat messages remain historical. Current project write authority, owner/folder permissions and connection grants are revalidated; stale conflicting revisions return 409. Exact retries return the current result without duplicate records. Separately edited Knowledge is fenced against accidental overwrites.

Knowledge-enabled Cloud answers retrieve authorized current captures and preserve source URLs, quote excerpts and historical capture dates in [K#] citations and answer source links. Native owner answers use the account-bound replica and [A#] citations, persisted in the original Brain/retrieval/history ledgers. Current paired VP3 delegation also retrieves annotations with Knowledge search authority and an unrestricted collection scope. Revoked pairing, opt-out, restricted collections and unrelated paired apps deny that context. Cloud folder-specific Knowledge scopes cannot be interpreted as native local collections, so delegated Knowledge retrieval is disabled for those turns; selecting an annotation explicitly remains available.

Knowledge sharing uses the existing same-account Cloud–HomeServer workspace synchronization. HomeServer reads complete canonical capture and Knowledge snapshots, rejects mismatched partial revisions and projects hash-only delivery receipts into its existing outbound Chat snapshot. Cloud reports **received** only when capture, delivery and Knowledge record hashes agree with the current canonical records. A newer edit returns to **pending** until acknowledged. Receipt timestamps are historical confirmations, not a live device heartbeat. No new Knowledge database, Chrome cache, local Knowledge row or model execution queue is created.

R5 uses the existing R4 table and schema 79. It requires matching Cloud, HomeServer and Chrome 22.15.0 releases; extension identity and pairing storage remain stable. Deploy Cloud first, then the Windows installer and extension. Connection recovery remains on hold.

Acceptance: actual MariaDB locally and MySQL 8 on PHP 8.1/8.3 in CI; real native SQLite/replica/Brain/history flows; controlled identity and transport faults; actual browser rendering for all three mobile canvases; retained Knowledge, capture, research, workspace, delegated inference and screenshot regressions. Live owner installation, hardware, model accuracy and provider availability are outside automated certification.
